# 過去ログAPI補完・コメント表示元選択 詳細設計

設計日: 2026-11-10。v1.0.2の実装方針。利用者向けの操作説明はREADMEを参照する。末尾に実装時の確認結果と差分を記載する。

## 1. 目的と決定事項

NicoBEで再生中の録画に対し、ニコニコ実況 過去ログAPIからコメントを取得する。NicoJKログ・動画内オリジナルコメントとの重複を除いて表示し、取得結果をNicoBE Encoder / CLIでも利用する。

- 自動取得は初期値ON。NicoJK・動画内・外部ASSの実況コメントがない場合のみ取得する。通常字幕は判定から除外。手動取得はこの条件にかかわらず利用可能。
- 左下の操作パネルに、コメント全体・表示元のスイッチと、取得状態・自動取得・取得ボタンを追加する。
- 表示元は「保存ログ」「過去ログ」「実況ASS」。保存ログにはNicoJKログと動画内オリジナルコメントを含む。
- 保存ログと過去ログは同時利用できる。実況ASSとの同時表示はしない。
- 個別スイッチはファイルを開くたびに自動選択し、その後の手動選択を優先する。
- API対象は放送時刻と実況チャンネルを解決できるTS系ファイル、および録画メタデータを持つNicoBE Encoder製MP4 / MKV。
- APIキャッシュは同一Windowsユーザーの両アプリで共有する。NicoJKのログへ追記・上書きしない。
- 追っかけ再生の直近部分はNicoJKを即時反映し、APIは5分間隔で遅れて補完する。
- Encoderは元コメントを統合・重複除去した後にMP4オリジナル / ASSを生成する。
- この設計のHTTP間隔はクライアント側の自主的な負荷制御。API運営者が許容頻度を保証したものではない。

## 2. 現状と変更箇所

| 現状 | 変更の理由 |
| --- | --- |
| `MainWindow`がTSを`LiveCommentSession`、MP4/MKVを`LogReader.Prepare`に振り分ける | メディア情報・取得元の一覧を先に確定し、複数ソースを統合する層が必要 |
| `PreparedComments`は基本的に単一の選択済みコメント一覧 | スイッチ操作に備え、元データと取得元を保持する必要がある |
| `LiveCommentSource`が描画用Commentへ変換して重複排除する | APIとの共通識別に必要な属性を失う前に統合する必要がある |
| `CommentEngine.SetComments`は表示中コメントを消し、履歴を復元する | APIの追加取得のたびには呼ばない。遅着コメントを遅れて流さない専用更新が必要 |
| `ContainerComments`は一般ASSも候補にできる | 読めることと、実況として自動選択・非表示にしてよいことを分離する |
| `SubtitleControl`には字幕が1本だけなら対象とする判定がある | 通常字幕を誤って消さないよう、確認済み実況トラックだけを制御する |
| `EncoderSettings.Validate`はコメント保存時にNicoJKフォルダを要求する | API / 共有キャッシュだけでもエンコード可能にする |
| 通常配置の保存先は各EXEの隣 | APIキャッシュのみ、配置によらない共通ユーザーディレクトリを追加する |

既存MP4メタデータとオリジナルコメント形式は変更しない。描画速度・文字サイズ・NG設定・シーク時の10秒分の履歴復元は維持する。

## 3. 対象ファイルと時刻

### 3.1 対象判定

| ファイル | API取得 | ローカルコメント再生 |
| --- | --- | --- |
| TS / M2TS / MTS | `TsReader`で放送時刻とサービス情報を取得でき、jk番号へ解決できれば可 | 従来どおり |
| MP4 | `Mp4RecordingMetadata`が有効で、jk番号へ解決できれば可 | メタデータがなくても既存オリジナル / 実況ASSは利用可能 |
| MKV | `NICOBE_RECORDING`が有効で、jk番号へ解決できれば可 | メタデータがなくても識別可能な実況ASSは利用可能 |
| 通常の動画・時刻不明 | 不可。ファイル名から推測しない | 読める既存コメントだけ利用 |

TSの開始直後に情報が不足している場合は「確認中」とし、既存のファイル更新通知で再判定する。ネットワークへは問い合わせない。

API用情報の読み出しはコメントの優先形式と独立させる。MP4のオリジナルコメント読み込み時に作る仮のUnixEpoch、ASSだけから作る仮のRecordingInfoをAPIへ渡してはならない。

### 3.2 時刻モデル

- 内部の投稿時刻はUTCの整数マイクロ秒とし、`date * 1_000_000 + date_usec`で作る。`date_usec`省略時は0。
- 区間は常に `[StartUtc, EndUtc)` の半開区間。
- TSは放送時刻、MP4/MKVは`PlaybackZeroUtc`を再生0秒とする。`SourceStartUtc`を代用しない。
- 描画へ渡す直前に `(投稿UTC - 再生0秒UTC)` を秒のdoubleへ変換する。
- APIのstarttime/endtimeは整数秒。必要区間を含む整数秒で要求し、応答を内部の半開区間に絞る。端数・隣接要求の重なりはこのフィルターと重複排除で処理する。
- 未来の時刻を要求しない。録画中の要求末尾は `min(確認できたTS末尾, 現在UTC)`。
- 取得時点のTS末尾と、再生カーソル位置は別。手動取得は先頭からその時点の末尾までの不足範囲を対象とする。

## 4. 設定とUI

### 4.1 永続設定

| 設定 | 初期値 | 範囲・用途 |
| --- | --- | --- |
| `Config.CommentsVisible` | 既存値を維持 | 全プレイヤー共通。トレイ・設定・パネルを同期 |
| `Config.AutoFetchPastLogs`（追加） | true | ローカル実況コメントがない場合のみ自動取得。全プレイヤー共通。パネル変更は保存して即時反映 |
| `EncoderSettings.UsePastLogComments`（追加） | false | Encoder / CLI用。キャッシュ利用と不足分のAPI取得を許可 |

個別ソースのON/OFFはプレイヤーごとのメモリ上の状態で、設定JSONには保存しない。同じ動画を別プレイヤーで開いても個別に選択可能。既存`CommentPreference`は、API全範囲取得前に保存ログと実況ASSの両方がある場合の初期選択に使う。

設定画面は「前方一致の外部ASS」「過去ログの自動取得」「NicoJK ログパス」の順に配置する。設定画面の編集中にパネル・トレイから共通設定が変わった場合、対応フィールドだけ表示と保存候補を同期し、ほかの未反映の編集を捨てない。

### 4.2 初回案内

> コメントの取得方法を設定してください。  
> NicoJKでコメントを保存している方は、NicoJKのログフォルダを指定してください。  
> 実況コメントがない動画は、再生時にインターネットから自動取得します（初期値ON）。左下の操作パネルから手動で取得することもできます。  
> コメント入りのMP4／MKVを再生する場合は、どちらも設定せずに利用できます。

NicoJKパス未指定かつ自動取得OFFでも設定完了可能。未指定はエラーにしない。指定されたパスが利用できない場合はそのソースの警告にとどめ、APIや動画内コメントを妨げない。

### 4.3 パネル構成

既存の「移動」「速度」の下に2行追加する。

```text
コメント [ON]  保存ログ [ON]  過去ログ [ON]  実況ASS [OFF]
過去ログ 取得済み          自動取得 [ON]  [取得]
```

- 本文・ラベル16 DIP、補助・ツールチップ14 DIP以上。狭い画面では折り返し、文字を縮小しない。
- 幅は既存を基本にし、内容に応じた高さで配置する。ホバー領域も追加行を含む概算寸法へ更新する。
- 非アクティブ時の表示、操作でフォーカスを奪わないこと、ポインタ離脱時の即時非表示を維持する。
- 設定の歯車は既存位置と動作を維持する。
- 取得中だけスピナーを表示。パネル非表示時はアニメーションを停止する。取得処理自体はパネルの表示寿命に依存しない。
- 全体OFFでもパネル操作は可能。個別選択を保持し、全体ONで同じ選択へ戻す。
- 全体OFF・個別表示OFFは通信停止を意味しない。自動取得ONで対象動画にローカル実況コメントがない場合は取得を継続する。
- API対象外では取得ボタンをDisableにして理由を表示する。全体設定の自動取得スイッチは操作可能とする。表示元の行は利用可能なソースについて操作可能とする。
- 通常字幕を操作するスイッチは作らない。

### 4.4 状態は別々に管理する

一つのenumに詰め込まず、次の状態の組み合わせから表示を作る。

| 軸 | 値の例 |
| --- | --- |
| 適格性 | 確認中 / 対象 / 対象外（理由付き） |
| 取得範囲 | なし / 一部 / 現在の対象範囲を取得済み |
| 更新可能性 | 暫定区間あり / 安定扱い |
| 通信 | 待機 / 他処理の完了待ち / 取得中 / 再取得待ち / 失敗 |
| 表示元 | 利用可能性、個別選択、手動選択済みフラグ |

表示優先順は「対象外・確認中」→「取得中・待機中」→「エラー」→「取得済み範囲」。エラー時も以前のキャッシュ範囲をツールチップに残す。

| 状態 | 表示 | ボタン |
| --- | --- | --- |
| 未取得 | 未取得 | 取得 |
| 進行中 | スピナー＋取得中 | Disable |
| 一部 | 一部取得済み | 不足分があり待ち時間終了なら取得 |
| 連続した範囲が先頭から取得済み | 21:15まで取得済み | 暫定区間なら5分待ち |
| 全範囲・安定扱い | 取得済み | Disable |
| 全範囲・安定扱い・0件 | コメントなし | Disable |
| 全範囲・暫定・0件 | コメントなし（更新待ち） | 待ち時間終了後に取得 |
| 失敗 | 取得失敗 | 待ち時間終了後に再試行 |

穴のある範囲を単純な最大時刻で「～まで取得済み」と表示しない。日時をまたぐ場合は日付も表示する。

全範囲取得済みの通常ボタンでは同じデータを取り直さない。過去の収集復旧等に備え、取得ボタン横のメニューに「この動画の過去ログを再取得」を置く。再取得でも同じ連打制限を適用し、成功までは既存キャッシュを保持する。

### 4.5 初期選択と優先順位

「利用可能」は、ファイルの存在だけでなく読み込めた表示対象コメントがあること。0件・解析失敗はONにしない。NG設定による非表示はこの判定から除外し、NGで全件非表示になってもソース選択を勝手に変えない。

| ソースの状況 | 初期選択 |
| --- | --- |
| 保存ログのみ | 保存ログON |
| 過去ログのみ（部分取得を含む） | 過去ログON |
| 保存ログ＋過去ログ、実況ASSなし | 両方ON、重複除去 |
| 実況ASSのみ | 実況ASSON |
| 保存ログ＋実況ASS、過去ログ未取得/一部 | 既存`CommentPreference`に従い保存ログまたは実況ASS |
| 実況ASS＋過去ログ一部、保存ログなし | 実況ASSON |
| 必要全範囲が安定扱いの過去ログ取得済みで表示コメントあり | 過去ログON、利用可能な保存ログON、実況ASSOFF（既存の優先形式より優先） |

- 実況ASSを手動ONにすると保存ログ・過去ログをOFFにする。
- 保存ログまたは過去ログを手動ONにすると実況ASSをOFFにする。
- 全ソースOFFも許す。ユーザーが意図して非表示にした状態を自動で戻さない。
- 個別スイッチを操作した時点で、そのファイル世代の自動選択を停止する。手動OFFだったソースが新たに利用可能になっても勝手にONにしない。
- 全体スイッチ・取得ボタン・自動取得スイッチの操作だけでは個別選択を固定しない。
- 未操作なら取得完了やログ到着に合わせて再判定する。ただし部分取得への更新で実況ASSを消さない。
- 動画が変わったら個別選択と手動フラグをリセット。同じファイルの設定再読込・取得更新・シークではリセットしない。
- 自動切替後にAPI通信が失敗しても、利用中キャッシュが有効なら表示元を戻さない。

## 5. 共有キャッシュ

### 5.1 保存先

製品では常に `%LOCALAPPDATA%\NicoBE\cache\jikkyo\v1\` を使う。Windowsユーザー単位の共有であり、他ユーザーとは共有しない。

これはAPIキャッシュ専用の例外。通常配置の設定・FFmpeg・出力動画はこれまでの配置ルールを維持する。`StorageLayout`へ`PastLogCacheDirectory`を追加し、Player/Encoder/CLIで同じ解決処理を使う。書き込み権限エラーで別の場所へ勝手に退避しない。

開発・検証では保存先を注入し、必ずリポジトリ内`temp/test-results`を使用する。設計・実装作業で実LocalAppDataへ試験データを書かない。

### 5.2 分割

- JSTの毎時00分・30分で30分区切り。ファイルキーは開始Unix秒で一意にする。
- 表示・日付ディレクトリはJST固定。OSタイムゾーン変更でキャッシュが分裂しないようにする。
- API要求の単位とは別。隣接する不足範囲を最大60分ずつまとめて取得し、ローカルで30分区間へ分配する。
- ファイル末尾や録画開始で区間の一部しか必要でない場合、その範囲だけを取得・管理してよい。

```text
v1/
  jk1/
    2026-11-09/
      1794225600.json                 # 21:00区間のマニフェスト
      1794225600.<generation>.xml     # XMLデータ
      ...
  control/
    network.lock                     # アプリ間の通信直列化
    network.json                     # 全体待機・Retry-After
    jk1.lock                         # チャンネル取得の排他
    jk1.json                         # 直近更新の次回可能時刻
```

### 5.3 データと管理情報

XMLは`packet/chat`形式を保ち、本文と属性を保存する。分割・統合により属性順やXMLエスケープ表現は変わってよいが、テキスト・属性値を加工しない。フィルター済みの描画用Commentをキャッシュに書かない。NicoJK・動画内のデータをAPIキャッシュへ混ぜない。

マニフェストには以下を持つ。

| 項目 | 内容 |
| --- | --- |
| `Version` | キャッシュ形式の版。初版1 |
| `Channel` | 検証済み`jk番号` |
| `BlockStartUtc` / `BlockEndUtc` | 30分区間の境界 |
| `Generation` / `DataFile` | この世代のXMLファイル名。ディレクトリ内の相対名に限定 |
| `DataSha256` / `DataBytes` | 完全性とサイズ確認 |
| `RecordCount` | 保存した元コメントの件数 |
| `Coverage` | 正常応答を得た時間範囲の配列。下記の取得日時・状態を範囲ごとに持つ |
| `UpdatedUtc` | マニフェスト更新日時 |

`Coverage`要素は`StartUtc / EndUtc / FetchedAtUtc / State`を持つ。`State`は`Provisional`または`Stable`。

- 0件の正常応答も取得範囲に含める。コメントがある最初・最後の時刻から取得範囲を推定しない。
- HTTPエラー、APIエラー、破損応答、途中切断は取得範囲に追加しない。
- 同じ範囲の再取得はその範囲のAPIデータを置換する。過去の応答を永久に足し続けない。範囲外のデータは維持する。
- 重複する要求境界は半開区間へ切り分け、範囲を正規化する。
- `Stable`は再取得を省略するクライアント上の扱いであり、提供元の完全性保証ではない。

### 5.4 安全な保存

1. チャンネルの排他を取得し、最新マニフェストを読み直す。
2. 新データを同じディレクトリの`.part`へ書き、解析・ハッシュを検証する。
3. 一意な世代名のXMLへrenameする。
4. 新マニフェストを一時ファイルへ書き、旧マニフェストと原子的に置換する。マニフェストの更新をコミットとする。
5. 読み手はマニフェストが示す世代だけを開く。ファイル未存在・ハッシュ不一致ならキャッシュ破損として不足範囲へ戻す。

XMLとJSONを順番に上書きするだけでは、異なる世代の組み合わせを読んでしまうので不可。中断した`.part`や参照されない古い世代は、利用中でないことを確認して次の利用時に掃除する。確定キャッシュの自動期限切れ・容量上限による削除は初版では導入しない。容量不足は警告し、既存キャッシュを保護する。

## 6. HTTP取得と追っかけ再生

### 6.1 取得要求

`https://jikkyo.tsukumijima.net/api/kakolog/{jk番号}` のXML形式を使う。要求には局IDと時刻だけを送り、ローカルパス・動画名・ユーザー設定を送らない。User-Agentは`NicoBE/<version>`または`NicoBE-Encoder/<version>`とプロジェクトURL。

| 制御 | 初版の値 |
| --- | --- |
| 1要求の時間範囲 | 最大60分（提供元の上限3日より小さい） |
| 同一ユーザーの同時通信 | Player/Encoder/CLIを合わせて1件 |
| 連続要求の間隔 | 前要求完了から最低5秒 |
| 暫定区間の再取得 | 同一チャンネルにつき、前回開始から最低5分 |
| HTTPタイムアウト | 60秒 |
| 応答本文上限 | 展開後64 MiB |
| 1コメント上限 | 既存の1 Mi文字上限を踏襲 |
| 1要求のレコード上限 | 50万件 |

上限超過は明示的なエラーとし、黙って先頭分だけを取得済みにしない。初版では失敗要求を自動的に大量の小要求へ分割しない。

応答はストリームで上限を監視する。XMLはDTD/外部実体を無効にし、APIがJSON形式のエラーを返した場合も失敗として扱う。chatの不正を検出した応答を完全取得として確定しない。既存のローカルログに対する不正レコードの読み飛ばしと、APIキャッシュの完全性判定は区別する。

1要求の上限とは別に、動画内へ保存する合計コメント数など既存のMP4出力上限も確認する。複数要求を結合して上限を超えたときに、黙って切り捨てて成功扱いにしない。

- 再生開始時・手動取得時は現在の再生位置を含む不足範囲を優先し、その後ほかの不足範囲を取得する。
- 手動取得は再生中のスナップショット範囲を一巡する。録画延長に無限追従しない。
- 自動取得ONへの変更時はローカル実況コメントがない場合のみ不足範囲を一度評価し、待機期限を守って取得する。確定済みなら通信なし。
- 自動取得OFFは新しい自動要求を止める。ほかの利用者がいない自動要求はキャンセルする。既に明示した手動取得・Encoderジョブは取り消さない。
- 取得ボタンは処理を1件だけ受け付ける。イベントハンドラー側でも多重実行を拒否する。
- ステータスを単にボタンのIsEnabledだけで制御しない。ファイル世代・共有待機期限を再確認してから実行する。

### 6.2 直近データと安定扱い

提供元は5分周期で収集し、その処理時間も必要。直近15分を暫定扱いとする。

- 正常応答の取得完了時刻をFとしたとき、要求範囲のうち`F - 15分`以前までをStable、それより後をProvisionalとする。
- **時間が経過しただけでProvisionalをStableへ変更しない。** 時間が経ってから再取得に成功した範囲をStableにする。
- 応答0件でも同じルール。直近の空応答で永久に取得を止めない。
- 後日サービス側の収集復旧・修正があった場合は、明示的な再取得で更新できる。
- 15分は実装上の余裕で、データ収集完了を保証しないことを説明に記す。

### 6.3 録画中

- 既存のTS更新通知で末尾時刻を延長する。更新がないことだけで録画終了と断定しない。
- NicoJKログは既存の通知ベースの追記読み込みを維持する。
- 自動取得は5分の単発タイマーで、延長分と再取得可能なProvisionalだけを計画する。新しい録画データがなくてもProvisionalが残れば更新対象。
- パネル非表示・一時停止中でも、動画を開いていて自動取得ONかつローカル実況コメントがなければ対象を維持する。
- 取得済み範囲が録画末尾までStableになり、その後TSが延長されなければネットワークタイマーを停止する。TSが延長されたら通知で再開する。
- ファイルを閉じたら、そのプレイヤーの利用権を解放する。閉じた動画を確定させるためだけにバックグラウンド取得を続けない。残りは次回利用時に取得する。

### 6.4 失敗・再試行

- タイムアウト、通信失敗、HTTP 5xxは、同じ失敗の自動再試行を5分→10分→20分→最大30分へ延ばす。
- HTTP 429は`Retry-After`を優先し、指定がなければ最低5分待つ。制限・拒否の回避はしない。
- 403等の拒否は、その取得ジョブの自動再試行を停止して表示する。認証情報の探索や別経路への迂回はしない。
- パラメーター不正・対象局不明は入力条件が変わるまで再試行しない。
- 正常な0件応答はエラーではない。
- 取得エラーはコメント機能内の状態表示にとどめ、映像再生や既存コメントを止めない。
- エラー内容・回数は診断ログへ残すが、コメント全文・投稿者IDを通信診断に列挙しない。

## 7. 複数プレイヤー・複数プロセス

### 7.1 同一NicoBE内

アプリ共通の`PastLogCoordinator`がチャンネル・時間範囲単位で要求をまとめる。各動画セッションはキャンセル可能な利用権を持つ。

- 同じ動画を2つ開いても1回取得する。
- 同じ局の重なる時間帯の別動画も、重複範囲を共有する。
- 片方を閉じても残りが必要なら続ける。最後の利用者が消えた場合だけ不要な要求をキャンセル。
- A→B→Aと切り替えても共有キャッシュ・待機期限を維持する。
- 完了通知にはメディア世代番号を付ける。キャンセル後や世代違いのUI更新を破棄する。

### 7.2 Player / Encoder / CLI間

初版は常駐仲介プロセスを増やさず、共有キャッシュと排他ファイルを使う。

- 取得単位の排他は`jk番号.lock`、全体の通信枠は`network.lock`。非共有で開いたFileStreamのハンドル寿命で管理する。asyncの継続先が変わる処理でスレッド所有Mutexを持ち越さない。
- ロック順はチャンネル→全体通信枠で固定。一度に複数チャンネルロックを持たない。
- 5分の待ち時間や再試行待ちの間はロックを保持しない。送信前にロックを取得して期限を再確認し、まだ待つ必要があれば解放して次回へ予約する。
- 再取得可能時刻は共有JSONに保存し、別アプリや再起動で5分待ちを迂回しない。予約は送信直前に記録する。
- 同じ区間を別プロセスが取得中なら待機し、完了後にキャッシュを読み直す。満たされた範囲は再送しない。
- 同一プロセス内は参照数で通信を共有。別プロセスの通信所有者が終了した場合はOSがロックを解放し、待機側はキャッシュ・待機期限を再評価して引き継ぐ。
- ロック待ちはキャンセル可能な疎な待機とし、利用者がいない時に巡回しない。クラッシュ後のロックファイルの存在だけで使用中と判断しない。
- キャッシュ更新通知は対象局・日付に限定したFileSystemWatcherを必要時だけ使い、通知をまとめてマニフェストの世代を確認する。Encoder自身の完了時は直接再読み込みする。

通信・監視の利用者が0になればタイマー・Watcher・大きなコメント配列・HTTP応答バッファを解放する。待機中の常時5分ポーリングは作らない。

## 8. 元コメントの統合・重複除去

### 8.1 内部モデル

描画用`Comment`へ変換する前に、`SourceComment`相当の本文・全属性を持つ内部レコードへ揃える。

- 取得元: NicoJK / EmbeddedOriginal / PastLogApi / Ass。
- 元の本文・属性を保持。比較用の正規化値は別フィールドで作る。
- 元レコードにはUTC投稿時刻または有効なメディア時刻、ソース内順序、比較用識別子を持つ。
- 同じ投稿の代表レコードに取得元の集合を持たせる。片方のスイッチをOFFにしても、もう片方に存在すれば残す。
- ASSはこの識別子による統合の対象外。

### 8.2 判定

第一段階は保守的な厳密判定とする。

1. チャンネル、投稿時刻（マイクロ秒）、thread、no、user_id、本文を比較用キーとする。
2. 補助属性の追加・属性順・mailの省略と空文字の違いは、同一投稿の判定を分ける理由にしない。
3. 本文の改行コードだけ比較用にLFへ揃える。空白の削除、全角半角変換、大小文字変換はしない。
4. 元の投稿者IDや属性値自体は加工しない。取得経路固有のID表現等は、実データで対応が確認できた場合だけ比較用アダプターで扱う。
5. thread/noが欠落したデータには、同じ投稿者ID・厳密な投稿時刻・本文で、**別取得元間の一対一対応**だけを補助判定する。同一ソース内の別コメントを本文だけで消さない。識別に必要な情報が不足すれば別件として残す。
6. 同一時刻・同一本文でも投稿者が違えば残す。時刻の丸めや数秒幅の近似一致はしない。

同一投稿の表示用代表はNicoJK→EmbeddedOriginal→APIの順に選ぶ。値が矛盾した属性を勝手に混成しない。元データを持つソースをOFFにしたら、残ったソースから代表を選び直す。

同一放送区間の実データで、NicoJK 112件とAPI 113件の対応を確認した。threadは`ch<数字>_<数字>`と`lv<数字>`で異なり、52件はdate_usecに1マイクロ秒差があった。同じno・user_id・本文でこの既知のthread形式の組み合わせに限り、1マイクロ秒以内を一対一対応とする。統合結果は113件。元属性は変更しない。未確認の経路や2マイクロ秒以上の差は別件として残す。

### 8.3 差分反映と負荷

- レコードIDのハッシュ索引と時刻順の索引を保持する。追加時に毎回全件比較・全件ソートしない。
- 新しいキャッシュ世代は該当時間範囲の追加・削除・更新差分を作る。
- 通常の取得完了では現在の描画位置と表示中コメントを保持し、既存全体を`SetComments`でリセットしない。
- 過去に遅れて到着したコメントは一覧に保持するが、今の画面へまとめて流さない。次回シークで対象になる。
- 保存ログとAPIに同じ投稿が到着しても、表示中に2個目を作らない。
- スイッチ操作・ASSとの切替時のみ、現在位置を基準に選択ソースのスナップショットを作り、既存のシーク復元と同様に10秒前からの履歴を構成する。半端な新旧リストを描画へ渡さない。
- ソース切替以外の更新では、表示を終えた過去コメントの削除が現在の描画に影響しないようにする。

## 9. 実況ASSと通常字幕

### 9.1 分類

ASSを解析できることと、実況と識別できることを分ける。

| 分類 | 根拠 | 自動選択・自動抑制 |
| --- | --- | --- |
| NicoBE実況ASS | トラック名`NicoBE Comments`、Script Info、独自スタイルを組み合わせて確認 | 可 |
| 既知ツールの実況ASS | NicoJK等の明示的名称と、実サンプルで確認した生成元・スタイルの特徴 | 確認済みルールのみ可 |
| 不明なASS | 汎用名、動く文字しか根拠がない | 不可 |
| 通常字幕・通常字幕との混在 | 実況専用と確定できない | 不可 |

`\move`の存在、字幕が1本だけという理由、動画名と同名という理由だけでは実況と断定しない。名前だけで混在がないことを保証せず、生成元と使用スタイルの組み合わせを確認する。不明なものを実況に手動指定するUIは初版の範囲外とする。

### 9.2 MPC-BEとの同期

- NicoBEが実況を表示する場合、MPC-BEで現在選択されているトラックが確認済み実況ASSに一致するときだけOFFにする。
- 通常字幕が選択されている場合は変更しない。字幕全体を無条件にOFFにしない。
- ネイティブMKVのトラック番号とMPC-BEの一覧番号は同じと仮定しない。名前等で一意に対応できない場合は自動操作をしない。
- 自動OFFの結果を応答で確認し、失敗・曖昧一致なら自動切替を完了扱いにしない。二重表示になる操作は保留し、パネルに理由を示す。
- 保存しておいた選択は同じファイル世代に限って復元する。別動画の字幕へ旧インデックスを送らない。
- NicoBEの全体OFFでは、自動的に消した実況ASSを勝手に復活させない。「コメントOFF」なのにコメントが残る矛盾を避ける。NicoBE終了・当該機能の解放時は、ユーザーが変更していなければ元の選択を復元する。
- MPC-BEでユーザーが字幕を選び直した場合はその操作を優先し、自動OFFを繰り返さない。確認済み実況ASSをユーザーが再選択したときは二重表示を避けて当該セッションのNicoBE描画を保留し、パネルに「MPC-BEで実況字幕を表示中」と示す。通常字幕への変更ではNicoBE描画を妨げない。

通常字幕と実況が同一ASS内に混在する場合の分離編集は行わない。元ファイルも変更しない。

## 10. Encoder / CLI

- コメントセクションに「過去ログAPIでコメントを補完」を追加する。GUI設定を保存し、CLIも同じJSONを読む。
- `EmbedComments`と`SaveExternalAss`が両方OFFならこの設定をDisableにする。保存値は保持するが取得を実行しない。
- オプションOFFは従来のNicoJKログだけ、ONはNicoJK＋共有キャッシュ＋不足分のAPI取得。Playerの自動取得設定とは連動させない。
- NicoJKフォルダなしでもONなら動作する。OFFでログがない場合も、既存の「コメントなし」警告で動画変換は継続できるよう、入口の必須パス検証を調整する。
- コメント準備段階で録画区間のスナップショットを取得し、共通の統合処理を通す。MP4では元本文・属性、MKV/外部ASSではその結果を描画用へ変換する。
- 時刻調整は既存の映像先頭PTS補正を維持する。API取り込み側と出力側で二重に補正しない。
- ネットワークエラー時は、取得済みキャッシュとNicoJKで続行し、未取得範囲・理由を完了結果とCLI出力へ警告する。取得できなかったことを成功と見せない。
- 直近のProvisionalデータが残る場合、Encoderを15分間待たせない。その時点のデータを使い、「直近のコメントは収集途中の可能性」を完了警告に出す。
- 取得中も中止操作を受け付ける。キャンセルは動画ジョブのキャンセルとして扱い、失敗時の続行へ変換しない。
- 更新され続ける入力TSを完全な録画として保証する変更はこの機能に含めない。Encoderの既存の入力条件は維持する。
- 画面・CLIは「コメントを取得」「共有取得の完了待ち」等の状態を表示する。HTTP待ちとエンコード進捗を混同しない。

## 11. 実装構成案

共通処理は既存のソースリンク方式を維持し、不要な新規NuGet依存は追加しない。新規コードは`src/NicoBE/PastLogs`および`src/NicoBE/Comments`にまとめる。

| モジュール案 | 責務 |
| --- | --- |
| `CommentMediaContextResolver` | メディア種別・再生0秒・末尾・局・API適格性。ASS選択と独立 |

| `PastLogClient` | HTTP、キャンセル、応答制限、XML/APIエラー判定 |
| `PastLogCache` | 30分分割、Coverage、世代付き原子的保存、破損検出 |

| Encoder | APIだけで生成、NicoJKと重複除去後のASS、MP4の元属性保持、失敗警告、中止、CLI設定・相対パス |

ネットワークは原則モック・保存済みXMLで検証する。実APIへの確認は少数の短い時間帯だけとし、頻度制限を探る試験はしない。実MPC-BEでの確認は代表的な再生・字幕切替・追っかけ再生に限定し、模擬確認と区別して報告する。

### 12.3 受け入れ条件

- 初回は自動通信せず、手動取得と明示的な自動取得ONでのみ不足範囲を取得する。
- 古い録画の必要範囲がキャッシュ済みなら再起動後も通信なしで表示する。
- 取得失敗・中断が既存ログ・キャッシュ・再生を壊さない。
- 個別スイッチが表示に反映され、通常字幕を誤って消さない。
- 複数プレイヤー・Encoder併用で同じ取得を重複実行しない。
- プレイヤーもEncoderジョブもないとき、新機能のタイマー・監視・大きなメモリを残さない。
- 変更前と同じソースだけを選択したとき、同期・改行・NG・速度・文字サイズを維持する。

## 14. v1.0.2での実装・確認

- 共通処理は`PastLogs/PastLogService.cs`・`PastLogCache.cs`・`PastLogEncoder.cs`。プレイヤーの寿命管理と表示元の選択は`Comments/PlaybackCommentSession.cs`で行う。
- キャッシュはXMLデータの世代ファイル＋SHA-256付きJSON。30分の端数も取得範囲を記録して保存する。確定済み扱いとAPI側の収集完了保証は別である。
- 実況ASSの自動識別はNicoBEとNicoDanmaku2ASSの既知の生成情報・スタイルに限定した。その他のASSを推測で実況扱いにはしない。
